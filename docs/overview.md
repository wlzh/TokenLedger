# 总体方案

状态：评审草案。项目名：TokenLedger。负责人：@wlzh。目标：约 5 至 100 人、允许员工自购 AI 订阅的小公司；人数是设计假设，不是经过负载测试的支持承诺。

## 1. 业务问题

购买记录、个人账号额度、本地 token 日志和公司报销分散在不同位置。管理者需要按员工组织这些信息，而不是再看几十个供应商的个人仪表盘。

产品定位为“员工授权上报、面向费用与采用情况的辅助管理系统”。不是推理网关、账号池、登录托管、考勤软件或防舞弊审计平台。

## 2. 核心原则

1. 保留员工自购和独立登录习惯，不集中收集供应商凭据。
2. 员工是主要业务维度，产品、账号、设备、模型是不同维度。
3. 钱、token、额度和活动时间分开建账，不能相互虚构换算。
4. 可信度和覆盖范围与数字一起展示；未知值不是零。
5. 集成既有接口优先，不首发维护两个大 Fork。
6. 管理端公网可登录，员工设备只主动出站上传。
7. 账户自报、日志采集和供应商账单具备不同证据强度。
8. 不以使用强度自动判定工作质量，不替员工执行购买或账号动作。

## 3. 路线比较

| 路线 | 长处 | 代价与局限 | 决策 |
|---|---|---|---|
| 两端 Fork 内置上报 | 单安装体验，可读取内部数据 | Swift/Rust 双维护、签名、更新与上游冲突 | 暂不采用 |
| 独立上报端适配 CLI | 低耦合、易禁用、保留原应用 | 多一个组件，接口粒度有限 | 主路线 |
| 拉取员工本地 HTTP | 读取快照方便 | 公网暴露、NAT、在线依赖 | 仅回环本地适配，不远程拉取 |
| 统一公司 API 网关 | 经网关流量易归因 | 无法直接覆盖个人订阅模式 | 后期可选数据源 |
| 官方组织分析 | 官方组织范围信息更可信 | 不覆盖各自个人账号的全部产品 | 后期可选对账源 |
| 手工月报 | 启动快 | 及时性与准确度低 | 保留为明确标记的补充通道 |

## 4. 推荐系统

```text
CodexBar / Win-CodexBar
         |
         | 本机选定账号的 JSON 输出 / 可选回环接口
         v
独立 Collector
  账号绑定 + 能力检查 + 规范化 + 白名单投影
  本地预览 + 加密待传队列 + 幂等批次
         |
         | 出站 HTTPS，只用本系统的设备凭据
         v
公司服务器：认证、接收、校验、归属、聚合、审计
         |
         v
管理员总览 / 员工详情 / 订阅台账 / 员工自助页
```

Collector 在员工操作系统用户上下文运行。管理端无法下发任意命令，无法索取供应商密码。周期触发为保底，钩子仅加速；所有读取受上游能力和员工授权约束。

## 5. 首版取舍

首版聚焦成员邀请、设备与账号绑定、额度快照、可获得的日级 token 汇总、订阅登记、数据健康和 CSV。首版购买记录不提供凭证文件上传，不以未完成的审批流程标识为已审核报销。

Cursor 的两端精度可能不同，按能力降级；不要为了跨平台画面一致伪造 token 字段。复杂多账号历史无法归属时保留员工/设备层统计和未归属标记。

高级费用审批、凭证附件、可解释的时间估算、提醒、SSO 和更广服务商集成分期推进。实现只从最小支持矩阵开始，不照抄上游服务商数量做宣传。

## 6. 财务价值与限制

可回答：公司承担哪些订阅；谁有多个重叠产品；选定范围内是否有使用；是否接近额度；哪份数据不新鲜；续费前需要问谁。

不可直接回答：员工一天真正工作几小时；全部个人 AI 活动；哪人 token 越多越有产出；每份订阅还剩多少美元价值；原始日志是否由员工修改。

订阅固定费用不按 token 使用比例自动摊销为“已消费现金”。年付可展示按服务期摊分的管理参考成本，必须与付款现金流分列，不宣称会计/税务记账结论。

## 7. 项目与交付方式

正式工程建议采用独立仓库，服务端、采集端和网页同一仓库管理；上游仅保留版本清单与测试夹具，不整仓 vendoring。新项目 MIT，保留引用和复用边界。开放自托管，不默认开通公共 SaaS。

本轮交付：文档包、设计契约、样例、风险及验收清单。未交付：程序、签名安装包、CI、数据库迁移、部署或兼容实测。

下一阶段顺序：确认文档 -> 授权使用脱敏样本 -> 最小两端采集验证 -> 审核支持矩阵 -> 决定实现范围。方案需保留回退空间，而不是以文档完成代替验证成功。
