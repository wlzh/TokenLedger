# 指标、费用与时间口径

状态：设计契约草案 `metrics/1`。任何口径调整都应有版本、生效时间和可重算方案。

## 1. 四个独立维度

| 维度 | 示例 | 必须避免 |
|---|---|---|
| 购买产品 product | Codex 订阅、Cursor 订阅、OpenRouter API | 把产品和实际调用模型混为一谈 |
| 模型 model | 来源报告的供应商命名空间 + 模型 ID | 仅按短名称合并不同供应商模型 |
| 供应商账号 account | 员工选择的一个平台账号/工作区 | 用当前邮箱回填全部历史 |
| 数据范围 scope | 账号总额、设备本地日志、工作区总额 | 将不同范围无条件相加 |

同一模型经不同购买产品使用，应分别归入产品消费；模型视图只是交叉分析，不新增一笔费用。

## 2. 每个指标的证据属性

除数值外，至少保留 `source_kind`、`source_scope`、`measurement_kind`、`coverage`、`attribution`、时间和单位。

| 属性 | 候选值 | 含义 |
|---|---|---|
| source_kind | provider_api / local_log / upstream_summary / manual_entry / invoice | 数据取得方式，不是可信评级 |
| source_scope | account / organization / device_log / profile_log / manual | 能覆盖的实际范围 |
| measurement_kind | reported / observed / estimated / declared | 报告值、观测值、估计值、申报值 |
| coverage | complete_in_scope / partial / unavailable / unsupported | 完整仅在所声明范围内有效 |
| attribution | source_verified / employee_asserted / unassigned | 历史账号归属证据 |
| freshness | current / stale / unknown | 由来源时间判断，不是上传时间 |

`provider_api` 通过员工机器转发时仍不是供应商签名证明。真实性还应标记 `verification=client_reported`；未来服务端官方对账使用不同证据流。

数值为 null 时必须给 `unavailable_reason`。只有来源确认该范围内零使用且覆盖完整时才显示 0。未知价格不产生 0 元。

## 3. Token 规范化

推荐规范化字段：`input_tokens_including_cache`、`cache_read_tokens`、`cache_write_tokens`、`output_tokens_including_reasoning`、`reasoning_tokens`、`total_tokens`。

- 不强行假设各平台的 input 包含缓存；适配器需逐源验证。
- 能可靠转换时，将普通输入、缓存读/写转换到统一输入总数；缓存分项是该总数的子集。
- 有 reasoning 分项时验证是否已经包含于 output，不能再重复相加。
- 统一总量只在字段含义确认后为 `input_tokens_including_cache + output_tokens_including_reasoning`。
- 如果只有上游 total，保留 total 与 `token_semantics=source_total_only`，其他分项未知。
- 不清楚上游字段是否重叠时，标 `source_native`，原生白名单字段保留供诊断，不给跨源统一总数。
- 使用安全整数/数据库大整数；超限拒绝而非溢出。JSON 协议用十进制字符串表达计数，见接口文档。

示例 A：输入总数 1000，缓存读 600，输出总数 200，推理 80。总数为 1200，不是 1880。

示例 B：来源明确输入字段不含缓存，普通输入 400、缓存读 600、缓存写 100、输出 200。规范化输入为 1100、总数 1300；适配器证据必须说明这种转换。

不把 token 不同分词器的数量比较包装为能力或产出比较。跨模型累计可用于量级展示，但必须保留来源与模型分布。

## 4. 额度快照

记录原生窗口标识、标签、周期、reset_at、used_ratio/remaining_ratio、原生上限与单位（若已提供）。统一 ratio 范围 0..1，原始百分比转换由适配器负责。

窗口标识不能仅靠“primary/secondary”猜测日/周；保留 cadence 未知。五小时额度窗口不是五小时工作时间。

额度快照是状态，不是可累加流水。相同账号在多设备上的快照保留各自来源，主视图选择最新有效数据并提示冲突，不能相加。

滚动窗口下降、供应商重置、赠送额度、手动 reset 都不直接推断为消费或退款。无法识别原因时只画状态趋势。

## 5. 金额与购买账

### 5.1 三种金额并列

| 字段类别 | 用途 | 汇总规则 |
|---|---|---|
| Cash payment / reimbursement | 实际付款或公司承担的支出 | 按币种、付款时间合计；退款作为独立反向记录 |
| Provider-metered consumption | API 扣款、套餐内计量或原生 credit 使用 | 保留计量单位与账期，不冒充现金 |
| List-price estimate | token × 对应价格规则 | 独立“估算”列，记录价格来源/生效时间/完整性 |

员工垫付 100 后公司报销 100，代表同一购买的两个付款事件，不算公司付出 200。平台充值 100，后续消耗 30，也不能汇总为花费 130。

所有购买记录有独立 purchase_id、paying_party、company_share、currency、paid_at、service_period。管理员补录仍是声明数据，除非有独立核验来源。报销申请与公司实付是不同状态。

### 5.2 价格估算

已知价格时按非重叠 token 类别分别计价。缓存读、缓存写的计价规则由版本化价格表提供。套餐固定金额、工具调用费、图片/音频/请求级费用、税费和折扣不通过 token 估算自动包含。

模型未知或价格缺失时保留未定价 token，展示“已知估算小计 + 未定价量”。价格表更新不能悄悄覆盖历史金额：保留原估算版本，可显式生成新版本报告。

### 5.3 币种和周期

默认保留原币种，不直接相加 USD 与 CNY。换算需指定汇率来源、日期、精度和目标币种；无汇率则分币种显示。金额以 decimal 字符串/高精度十进制存储，不用浮点处理付款。

现金流按付款日期，服务期参考成本按明确的起止日分摊，两个图表分开。此分摊只作管理参考，不提供会计或税务判断。

原生 credits 默认不可换算成美元，除非该账期有供应商明确兑换规则并保留证据。

## 6. 时间口径

### 6.1 首版可用指标

- `last_activity_at`：实际使用事件的时间，不是 Collector 心跳。
- `active_days`：存在可确认使用事件的自然日数，依源时区注明。
- `last_collection_at`：最近成功读取源数据时间。
- `last_upload_at`：最近服务器接收时间。
- `coverage_intervals`：该来源可覆盖的时间范围，不把轮询覆盖误认为使用覆盖。

只有日级汇总时，可以统计有正数用量的日期，不能声称知道具体时段。

### 6.2 后期活跃时长估算

候选规则 `activity/1`：将可靠事件时间映射为 `[t, t + 5 分钟)` 区间，再与已知可采集/授权范围相交、合并重叠区间。5 分钟是待验证的估算参数，不是事实。午夜与授权边界拆分；一天不得超过实际自然日长度（夏令时可能不是 24 小时）。

同一员工跨模型/设备总活跃时长取并集；逐模型时长允许重叠，因此各模型之和可能大于员工总时长，界面必须说明。单个事件也会形成估算区间，不能标为精确运行时间。

没有事件时间则时长未知。仅 `started_at` 与 `last_activity_at` 可显示会话跨度，但不纳入活跃时长。夜间自动 agent 工作标为 AI 活动，不算人在岗。

任务运行时长只能来自明确开始/完成事件。崩溃或缺结束事件标 incomplete，不用当前时间一直累加。

## 7. 时间窗口与时区

事件存 UTC，组织选择 IANA 时区显示与汇总。只有源日级数据时同时保存 source_bucket_timezone 与源起止时间，不凭 UTC 午夜硬切到组织日期。无法重新分桶的来源保留源日期并注明，不能混在同一“精确本地日”图表里。

历史导入首版默认从授权起始点开始。纯日级混合数据跨越授权起点时，整桶不上传或经员工明确授权整日回填；不能按小时比例估算拆分。

## 8. 去重、修订与多来源

事件级：稳定事件 ID + 来源命名空间 + 隐私安全账号/逻辑来源标识去重。仅时间/token 相同不能视为同一请求。没有稳定 ID 就不承诺跨设备精确去重。

聚合级：以 source_scope_id、metric_family、模型、固定起止、源时区为键，提交新 revision 替换该范围旧值，保留修订轨迹；重复读取“最近 30 天”不可追加。

同一账号官方累计与本地请求明细是可比较证据，不是两个可相加来源。报告选择一条覆盖可解释的主数据路径，其他作为对账差异。两个设备日志若有镜像风险，员工选择权威来源或保留独立列，禁止自动合并。

历史日志在同设备混过多个账号时，默认未归属；员工手动认领属于 employee_asserted，有生效范围和审核记录，不升级为 source_verified。

## 9. 报告中的解释

每张图/导出应含范围、单位、时间口径、来源、完整性和估算说明。员工本地时间、服务商账期与组织时区不一致时不得隐藏。

“可能闲置”规则只在覆盖充分且持续有上报时计算；数据缺失时写“无法判断”。余额不足告警可提示员工，不自动追加采购。tokens per dollar 只在可比同口径范围展示，不输出自动绩效排名。

## 10. 必测向量

| 向量 | 预期 |
|---|---|
| 1000 input 含 600 cache + 200 output 含 80 reasoning | total=1200 |
| 同一日汇总 100 -> 120 -> 重传 120 | 最终 120，不是 340 |
| 两设备同账号 40% 与 45% | 主值最新有效 45%，不为 85% |
| 付款100、报销100、估算500 | 公司实付按承担记录100，估算500独列 |
| 充值100、消费30 | 现金支出100，计量消费30，不合计130 |
| 账号A旧日志、当前登录B | 不自动归给B |
| 不可读来源与零使用来源 | 分别 unknown 与 known-zero |
| 缺价模型10万token | token可显示，费用未知而非0 |
| 断网补发上周数据 | 放回原周期，不能当今日消费 |
